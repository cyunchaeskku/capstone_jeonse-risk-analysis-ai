# 전세사기 위험도 판별 핵심 로직

이 문서는 프로젝트의 **판단 로직 단일 기준(Single Source of Truth)** 이다.
`deep-research-report.md`, `jeonse-checklist_1.md`, `jeonse-checklist_2.md`, `doc-vs-data.md`,
`specs/risk-analysis.md`, `adr/0002-risk-engine-approach.md` 에 흩어져 있던 판정 기준을 여기에 통합했다.
임계값이나 규칙을 바꿀 때는 **이 문서를 먼저 고치고** 코드를 맞춘다.

---

## 0. 판단 원칙

1. **판정은 규칙, 설명은 LLM.** 규칙 엔진이 `status`를 결정하고, LLM은 그 결과를 자연어로 풀어쓰기만 한다.
   LLM은 판정값을 바꾸지 않는다. (ADR 0002)
2. **모르면 `unknown`.** 데이터가 없으면 `pass`로 넘기지 않는다. `unknown`은 점수 0점이지만
   사용자에게는 "확인 필요"로 노출한다. 미탐(false negative)을 안전한 통과로 위장하지 않기 위함이다.
   담보 여력 규칙(R1·R2·R8)이 **전부** `unknown`이면 종합 등급에도 바닥을 둔다(§4-2).
3. **모든 판정은 근거(evidence)를 남긴다.** 각 규칙은 계산에 쓴 원본 수치를 `evidence`에 담는다.
   점수만 있고 근거가 없는 판정은 만들지 않는다.
4. **데이터로 자동 판정 가능한 것과 사람이 눈으로 확인해야 하는 것을 분리한다.**
   전자는 §3 규칙 카탈로그, 후자는 §6 수동 체크리스트.
5. **자동 판정은 계약 결정을 대체하지 않는다.** 최종 출력에는 항상 전문가 확인 권고를 포함한다.

## 1. 위험의 구조 (무엇을 판별하려는 것인가)

전세사기의 본질은 **"계약 종료 시 보증금을 돌려받지 못할 위험"** 이다. 이 위험은 세 층으로 나뉜다.

| 층위 | 질문 | 대표 사기 유형 |
|---|---|---|
| **A. 담보 여력** | 집이 경매로 넘어가면 내 보증금이 남는가? | 깡통전세, 무자본 갭투자 |
| **B. 권리 순위** | 내 앞에 누가 서 있는가? | 선순위 근저당, 이중·삼중 계약, 다가구 선순위 보증금 |
| **C. 계약 정당성** | 계약 상대가 진짜 처분 권한자인가? | 소유자 불일치, 대리인 사칭, 신탁 오도, 계약 후 대출 실행 |

**핵심 부등식** — 모든 금액 규칙은 결국 이 하나로 수렴한다.

```
(선순위 채권최고액 + 선순위 보증금 총액 + 내 보증금) / 주택 시세  ≤  0.8
```

좌변이 1을 넘으면 경매 시 원금 손실이 사실상 확정이고, 0.8은 경매 낙찰가율(통상 70~80%)과
경매 비용을 감안한 안전 마진이다. §3의 전세가율·근저당비율·선순위보증금 규칙은
이 부등식을 **데이터 확보 가능한 항목별로 쪼갠 것**이다.

## 3. 규칙 카탈로그

각 규칙의 `status`는 `pass` / `warn` / `fail` / `unknown` 중 하나다.

### R1. 전세가율 — `deposit_to_market_ratio` · 가중치 15 · **구현됨**

- **계산**: `ratio = 보증금 / 시세`
- **판정**: `ratio > 0.80` → `fail`, 그 외 `pass`, 시세 미확보 → `unknown`
- **적용 조건**: 집합건물 전용. 등기 유형이 `general_building`이면 **`unknown`**.
  다가구는 시세가 건물 전체 기준이라 호실 하나의 보증금은 비율이 구조적으로 낮게 나와
  항상 `pass`가 된다. 다가구의 담보 여력은 R8이 판정한다.
- **점수**: 계단이 아니라 비례 배점(§4-2). `ratio`가 0.60~1.00 구간에서 선형으로 0~15점.
- **근거**: 보증금이 시세의 80%를 넘으면 경매 시 원금 손실 구간에 들어간다.
- **시세 산출 우선순위**: ① 사용자 입력 `market_price_krw` → ② 동일 건물 최근 매매 실거래가
  → ③ 보증금 × 유형별 배수(`apt 1.35 / offi 1.28 / rh 1.22 / sh 1.18`, **임시 mock**)
- **주의**: ③은 실거래가 API 승인 전 임시값이다. mock 배수는 보증금에서 역산하므로
  전세가율이 항상 안전하게 나온다 — 즉 **③ 경로일 때 이 규칙의 `pass`는 신뢰할 수 없다.**
  실거래가 연동 후 ③을 제거하고 `unknown`으로 바꿔야 한다.
- 구현: `_run_deposit_to_market_check()` @ `backend/app/main.py:839`

> **임계값 확정 근거**: `deep-research-report.md`는 85%, 체크리스트는 80%를 쓴다.
> 공적 체크리스트(국토부·HUG) 기준인 **80%로 통일**한다.

### R2. 근저당 비율 — `mortgage_ratio` · 가중치 30 · **미구현 (등기 연동 대기)**

- **계산**: `ratio = 유효 채권최고액 합계 / 시세`
- **판정**: `ratio > 0.60` → `fail`, `0.40 < ratio ≤ 0.60` → `warn`, `≤ 0.40` → `pass`, 등기 미제출 → `unknown`
- **합산 판정 (R2-b)**: `(채권최고액 + 내 보증금) / 시세 > 0.80` → `fail`.
  근저당 단독으로는 60% 미만이어도 보증금과 합쳐 80%를 넘으면 위험하다. **§1 핵심 부등식의 직접 구현.**
- **채권최고액 산정**: 말소되지 않은 근저당만 합산. 변경 등기가 있으면 마지막 금액을 유효값으로 보되,
  `is_cancelled = null`(말소 불확실)인 항목은 **보수적으로 유효로 간주**하고 `needs_human_review`를 세운다.
- **필요 입력**: `registry_inspection: dict` (필수 필드로 추가 — `Optional = None`으로 넣지 말 것)
- 상태: `_CHECK_WEIGHTS`에 가중치만 등록되어 있고 규칙 함수는 없다.

> **임계값 확정 근거**: 체크리스트 60%, deep-research 80%. 단독 근저당 기준은 **60%**(체크리스트),
> 보증금 합산 기준은 **80%**(§1 부등식)로 역할을 나눠 둘 다 살린다.

### R3. 소유자 일치 — `owner_mismatch` · 가중치 15 · **미구현 (프론트 입력 필드 대기)**

- **판정**: 계약서상 임대인명 ≠ 등기부 갑구 현재 소유자명 → `fail`, 일치 → `pass`, 어느 한쪽 없음 → `unknown`
- **공동소유**: 소유자가 복수면 계약 당사자에 **전원이 포함**되어야 `pass`. 일부만이면 `fail`.
- **필요 입력**: `contract_owner_name: str` (필수 필드) + 프론트 입력 UI
- **자동 판정 한계**: 이름 일치는 위조 신분증·무권 대리를 걸러내지 못한다.
  `pass`여도 §6의 신분증·위임장 확인 항목은 항상 노출한다.

### R4. 권리침해 — `rights_encumbrance` · 가중치 30(오버라이드) · **부분 구현 (LLM 추출까지)**

- **탐지 대상**: 압류, 가압류, 가처분, 가등기, 경매개시결정, 신탁
- **판정**: 말소되지 않은 항목이 하나라도 있으면 → `fail` + **고위험 오버라이드**(§4)
- **신탁 특칙**: 신탁등기가 유효하면 처분 권한이 수탁자(신탁회사)에 있다.
  등기부상 소유자와 계약해도 무효가 될 수 있으므로, R3가 `pass`여도 신탁이 있으면 `fail`.
  → "신탁회사 동의서 또는 계약 권한 확인 필요" 안내를 강제한다.
- **파이프라인**: 등기부 PDF 업로드 → `registry_inspector.py`가 LLM으로 갑구 항목 추출 →
  `_reject_unsourced_critical_terms()`가 원문에 실제로 등장하지 않는 항목을 기각(환각 방어) →
  프론트가 `critical_terms`로 `/risk/assess`에 전달 → `_run_rights_encumbrance_check()`.
  `is_cancelled`가 `true`가 아닌 항목은 모두 유효로 본다(말소 불명 → 보수적으로 활성).
- **환각 방어가 필요한 이유**: `critical_terms` 한 건이 곧바로 30점 + 고위험 오버라이드를
  트리거한다. 오탐 1건이 멀쩡한 매물을 고위험으로 낙인찍으므로, 원문에 실제로 등장하는 단어만 통과시킨다.

### R5. 건축물 용도 — `residential_use` · 가중치 15 · **구현됨**

- **판정**: `building_type + detail_use` 문자열에 주거 키워드
  (`공동주택 / 단독주택 / 다가구 / 다세대 / 연립 / 주택 / 오피스텔`)가 있으면 `pass`, 없으면 `fail`, 정보 없음 → `unknown`
- **근거**: 근린생활시설·고시원·업무용 오피스텔은 전세보증보험 가입이 제한되고
  주택임대차보호법 적용 여부가 다툼이 될 수 있다. (근생빌라 유형)
- **알려진 결함**: `오피스텔`을 주거 키워드에 넣어 두어 **업무용 오피스텔이 `pass`로 빠진다.**
  `업무` 포함 시 제외하는 예외를 추가해야 한다.
- 구현: `_run_residential_use_check()` @ `backend/app/main.py:925`

### R6. 위반건축물 — `illegal_building` · 가중치 15 · **v1 미노출 (의도적)**

- **판정**: 건축물대장 위반건축물 표시 존재 → `fail`
- **근거**: 위반건축물은 보증보험 가입이 거절되고 시정명령·이행강제금 대상이 된다.
- 상태: 데이터 소스 연결 전까지 노출하지 않기로 확정(`specs/risk-analysis.md`). 건축물대장 응답의
  위반 표시 필드를 매핑하면 바로 켤 수 있다.

### R7. 전세 거래 집중도 — `duplicate_contract` · 가중치 25 · **구현됨 (약한 프록시)**

- **계산**: 최근 3년 순수 전세 중 갱신계약을 제외하고, 가장 거래가 집중된 연속 12개월의
  `거래 건수 / 총 세대수`를 계산한다.
- **판정**: 일반건물에서 `12개월 신규 전세 >= 3건`이고 `총 세대수의 30% 이상`이면 `warn`,
  그 미만이면 `pass`. 집합건물은 호실별 소유자가 다를 수 있어 점수에 반영하지 않고 참고 정보로만
  제공한다. 조회가 일부만 완료되거나 총 세대수가 없으면 `unknown`.
- **근거**: 이중·삼중 계약은 동일 건물에 전세 계약이 비정상적으로 몰리는 형태로 나타난다.
- **한계**: 실거래 신고 데이터만으로 실제 이중계약을 확정할 수 없다. 일반건물에서도 참고 신호이며
  `fail`이 아니라 `warn`이 최대치다. 30%·3건 기준은 사례 검증 후 조정이 필요한 초기 휴리스틱이다.
- 구현: `_run_duplicate_contract_check()` @ `backend/app/main.py:890`

### R8. 선순위 보증금 (다가구) — `senior_deposit` · 가중치 30 · **수기 입력**

- **적용 조건**: 등기 유형이 `general_building`(일반건물 = 단독·다가구)일 때만.
  집합건물(`aggregate_building`)은 호실별 등기라 해당 없음.
- **판정**: `(선순위 보증금 합계 + 채권최고액 + 내 보증금) / 시세 > 0.80` → `fail`
- **데이터 한계**: 선순위 보증금은 등기부에 나오지 않는다. 전입세대 열람원 + 확정일자 부여현황을
  주민센터에서 받아야 한다. **API가 없다.**
- **현재 동작**: `registry_inspector.py`가 일반건물로 판별하면
  "먼저 들어온 세입자들의 총 보증금(선순위 보증금)을 추가로 확인해야 합니다"를 findings에 강제 삽입한다.
  사용자가 확인한 합계를 입력하면 자동 판정하고, `확인하지 못함`을 선택하면 `unknown`으로 판정한다.
  실제 선순위 보증금이 없음을 확인한 경우에만 `0`을 입력한다.

### R9. 보증보험 가입 가능 여부 — `guarantee_eligibility` · 가중치 미배정 · **미구현 (API 없음)**

- **근거**: HUG/HF/SGI 가입 가능 여부는 위 R1·R2·R5·R6를 기관이 자체 심사한 **종합 결과**다.
  가입 불가는 강력한 위험 신호다.
- 상태: 공식 API가 없어 자동 판정 불가. §6 수동 체크리스트로만 안내한다.
- **대안 규칙**: R1·R2·R5·R6 중 하나라도 `fail`이면
  "전세보증보험 가입이 거절될 가능성이 있습니다"를 설명 계층에서 안내한다.

| `deposit_to_market_ratio` | R1 전세가율 | 15 | ✓ |
| `residential_use` | R5 건축물 용도 | 15 | ✓ |
| `owner_mismatch` | R3 소유자 일치 | 15 | ✓ |
| `illegal_building` | R6 위반건축물 | 15 | ✓ |
| | **원점수 합계** | **175** | |

> 원점수 합계가 100점을 넘어도 최종 위험 점수는 100점에서 상한 처리한다.
> 실제 값: `_CHECK_WEIGHTS` @ `backend/app/main.py`

### 4-2. 점수 공식

R1·R2-b는 **비례 배점**, 나머지는 계단 배점을 쓴다.

```
# 계단 (R3~R8)
step(rule)  = weight       if status == "fail"
            = weight // 2  if status == "warn"
            = 0            if status == "pass" or "unknown"

# 비례 (R1, R2-b) — 부담률 60%~100%를 선형으로
prop(ratio) = 0                                      if ratio <= 0.60
            = weight                                 if ratio >= 1.00
            = round(weight * (ratio-0.60) / 0.40)    otherwise

score(R1)   = prop(보증금 / 시세)
score(R2)   = max(step(근저당 단독 비율), prop(합산 부담률))

risk_score  = min(Σ score, 100)

# 바닥 (§0-2)
R1·R2·R8이 모두 unknown이면  risk_score = max(risk_score, 15)
```

**비례 배점을 쓰는 이유.** 계단 배점에서는 전세가율 79.9%가 0점, 80.3%가 45점이었다.
0.4%p 차이로 `안전`과 `위험`이 갈리는 절벽이 생기고, 반대로 80.3%와 99.6%가 똑같이 45점이라
그 구간 안에서는 위험의 크기를 전혀 구분하지 못했다(포화). §1 부등식은 연속량이므로 점수도 연속이어야 한다.
`status`는 그대로 임계값으로 판정하고(사용자에게 보여줄 정성 판단), 점수만 비례로 매긴다.
따라서 **모든 카드가 `pass`여도 부담률이 높으면 등급이 `주의`가 될 수 있다.**

**R2-a는 왜 계단으로 남기나.** 합산 부담률만 비례로 계산하면 보증금이 작고 근저당이 큰 물건의
점수가 내려간다. 근저당 단독 비율의 계단 판정과 비교해 **큰 값**을 쓴다.

**바닥 점수를 두는 이유.** §0-2는 `unknown`을 "확인 필요"로 노출하라고 정했지만 등급 계산에서는
`pass`와 똑같이 0점이었다. 그 결과 선순위 보증금을 확인하지 못한 다가구는 R1·R2·R8이 모두
`unknown`이 되어 **0점 `안전`** 으로 표시됐다. 담보 여력을 하나도 보지 못한 상태를 `안전`이라고
말하지 않기 위해 최소 15점(`주의`)을 준다.

구현: `_compute_risk_score()` @ `backend/app/main.py:879`

### 4-3. 종합 상태 (구현됨)

개별 `status` 중 가장 나쁜 것을 그대로 승격시킨다. `fail > warn > unknown > pass`
구현: `_summarize_check_overall()` @ `backend/app/main.py:787`

### 4-4. 위험 등급 (구현됨)

`risk_score`는 반환되지만 등급 구간이 없다. 구간은 다음으로 확정한다.

| 점수 | 등급 | 사용자 안내 |
|---|---|---|
| 0–14 | 안전 | 주요 위험 신호 없음. 수동 체크리스트는 그대로 수행 |
| 15–29 | 주의 | 확인이 필요한 항목 존재 |
| 30–59 | 위험 | 계약 전 전문가 상담 권고 |
| 60–100 | 고위험 | 계약 재고 권고 |

> `deep-research-report.md`의 구간(≥70 고위험 / 40–69 주의 / <40 정상)은 **이 가중치 테이블과 맞지 않는다.**
> 근저당 비율 단독 `fail`(30점)이 "정상"으로 분류되기 때문이다. 위 구간으로 대체한다.

### 4-5. 고위험 오버라이드 (구현됨)

다음 중 하나라도 해당하면 **점수와 무관하게 즉시 `고위험`** 으로 확정한다.
가중 합산은 "치명적 단일 결함"을 평균으로 희석시키기 때문이다.

- R4: 말소되지 않은 압류·가압류·경매개시결정·신탁이 존재
- R3: 계약서상 임대인 ≠ 등기부상 소유자
- R2-b: `(채권최고액 + 내 보증금) / 시세 > 0.90`
  > 임계를 1.0에서 0.90으로 내렸다. 낙찰가율이 통상 70~80%이므로 90%면 배당만으로는 사실상
  > 전액 손실이다. §1이 안전 마진을 0.8로 잡아 놓고 오버라이드만 1.0으로 두는 것은 느슨하다.
  > 근거 사례: 서울중앙 2024타경117502(전세가율 96.6%, HUG 대위변제 사고). 1.0 기준에서는
  > 45점 `위험`에 그쳤다.

## 5. 등기부등본 LLM 검토 로직

등기부는 비정형 PDF라 규칙만으로 파싱할 수 없다. **2단계 하이브리드**로 처리한다.

```
PDF → ① deterministic parser (PyMuPDF + 정규식)  → 채권최고액 후보
    → ② LLM 구조화 추출 (①의 결과를 컨텍스트로 주입) → 구조화 JSON
    → ③ 규칙 엔진 (R2·R3·R4·R8)                    → status 판정
```

- ①의 역할: 금액 추출. **금액 숫자는 LLM이 만들지 않는다.** (`registry_parser.py`)
- ②의 역할: 표제부/갑구/을구 구조 해석, 말소 여부 구분, 위험 단어 탐지. (`registry_inspector.py`)
- ③은 아직 연결되지 않았다 — 현재 ②의 결과는 화면 표시용으로만 쓰인다. **이것이 가장 큰 미완성 구간이다.**

### LLM에 강제한 제약 (프롬프트 원칙)

- 위험도 **계산을 하지 않는다.** 추출만 한다.
- deterministic parser가 계산해야 할 값을 지어내지 않는다.
- 원문에 없는 정보는 `null` / 빈 배열.
- 말소 여부가 불확실하면 `is_cancelled: null` (false로 단정 금지).
- 주민등록번호 뒷자리는 절대 출력하지 않는다.
- **좋은 신호도 반드시 findings에 포함한다** (severity `info`). 위험만 나열하면 사용자가 과잉 공포에 빠진다.
- 출력은 JSON만.

### 섹션별 추출 항목

| 등기 섹션 | 추출 | 연결 규칙 |
|---|---|---|
| 표제부 | `registry_type`(집합건물/일반건물/토지), `main_use`, 위험 용도어 | R5, R8 적용 여부 결정 |
| 갑구 | 현재 최종 소유자(순위번호 마지막·미말소), 압류·가압류·가처분·가등기·경매·신탁 | R3, R4 |
| 을구 | 근저당 채권최고액(말소 구분), 전세권·임차권등기·지상권 | R2 |

`needs_human_review`는 기본 `true`다. 자동 검토가 사람 확인을 대체하지 않는다는 것을 출력 구조 자체에 박아둔다.

전체 스키마와 프롬프트: `backend/app/registry_inspector.py:11`

## 6. 수동 체크리스트 (자동 판정 불가 — 사용자에게 반드시 안내)

자동화할 수 없지만 실제 피해의 상당수가 여기서 갈린다. 분석 결과 화면에 **단계별로** 노출한다.

### 6-1. 계약 전

- [ ] 등기부등본을 **오늘 날짜로** 다시 발급받았는가 (열람용 아닌 최신본)
- [ ] 등기 없는 신축 건물은 아닌가 — 등기부가 없으면 권리 확인 자체가 불가능
- [ ] 국세·지방세 완납증명서를 받았는가 — **체납 세금은 등기부에 없지만 보증금보다 우선한다**
- [ ] 다가구인 경우 전입세대 열람원 + 확정일자 부여현황으로 선순위 보증금을 확인했는가 (→ R8)
- [ ] 건축물 현황도와 실제 구조·호수가 일치하는가
- [ ] 지역별 최우선변제금 기준을 확인했는가 (담보물권 설정일 기준으로 달라짐)
- [ ] 공인중개사 자격증·개설등록증·공제증서를 확인했는가

### 6-2. 계약 시

- [ ] 계약하러 나온 사람이 등기부상 소유자 본인인가 (신분증 대조)
- [ ] 소유자가 여러 명이면 **전원과** 계약하는가
- [ ] 대리인이면 위임장 원본 + 위임자 인감증명서 + 인감도장 일치 + 양측 신분증
- [ ] 보증금 입금 계좌의 예금주가 소유자 명의인가
- [ ] 주소·면적·동호수가 건축물대장·등기부와 일치하는가
- [ ] 중개대상물 확인·설명서를 교부받고 설명을 들었는가
- [ ] **특약 삽입**: "확정일자·전입신고 다음날까지 담보권 설정·소유권 변경 금지, 위반 시 즉시 해지 및 손해배상"
- [ ] **특약 삽입**: "전세보증금반환보증 가입 불가 시 계약 무효, 보증금 반환"
- [ ] 임차인에게 일방적으로 불리한 특약이 없는가

> 담보권 설정 금지 특약은 **"계약 당일 대출 실행"** 유형에 대한 유일한 방어 수단이다.
> 대항력은 전입신고 다음날 0시에 발생하므로, 그 사이 하루의 공백을 임대인이 노린다.

### 6-3. 잔금·입주

- [ ] 잔금 지급 **전** 등기부등본을 재발급해 갑구·을구 변동을 확인했는가
- [ ] 주택 인도(열쇠·도어락 비밀번호)를 받고 잔금 지급과 동시에 입주하는가
- [ ] 전입신고를 했는가 → **대항력** (인도 + 전입신고 다음날 0시 발생)
- [ ] 확정일자를 받았는가 → **우선변제권** (대항력 + 확정일자)
- [ ] 주택임대차계약 신고를 했는가 (신고대상인 경우)
- [ ] 전입신고 일주일 후 등기부를 재확인해 신규 설정 권리가 없는지 확인했는가

## 8. 예외 처리
